MCP Tasks · Kubernetes lab

Possession is not permission: who owns an MCP task?

When one authenticated agent holds another agent's MCP task ID, what can it do, and where can an owner check stop it? This lab measures it on a local Kubernetes cluster, in the server, in front of an unchanged server, and in a gateway.

Repository Run it yourself Results

The problem

The MCP Tasks extension (specification 2026-07-28) lets a server answer a long tools/call with a task ID. The client then polls it, can cancel it, and can answer a question the task asks along the way.

tasks/get

read the result: confidentiality

tasks/cancel

stop long-running work: availability

tasks/update

answer an approval prompt: integrity

The specification asks for both of these:

Servers MUST perform authentication and authorization checks on each task-related request to ensure that the client has permission to access a task.

A server MAY use task IDs as bearer tokens for a server's stored state.

It defines no way to bind a task to the principal that created it, and sessions, the scope originally planned for this, have been removed from MCP. On a shared MCP server, where several teams' agents run on one cluster, a task ID that leaks through a log, a persisted client store or an agent's context is enough for another team's agent to act on the task.

This is not a vulnerability report: bearer task IDs are permitted. Per-owner isolation is a stricter policy that shared deployments may need; the lab measures how and where it can be enforced.

The approach: a task handle sealed to its owner

MCP already has a rule for an opaque value that a server issues and the client sends back, requestState: if it influences authorization, protect its integrity and bind it to the caller and a short expiry. The lab applies the same rule to task IDs.

client sees:  v1.<base64url(nonce || AEAD(payload))>
payload:      {target, upstream task id, owner: {iss, sub, azp}, exp}
  • The upstream task ID never reaches the client, only the sealed handle does.
  • On every task request the handle is opened and its owner compared with the caller's token. Another owner, a tampered or expired handle and an unknown ID all get the same unknown task error.
  • Any replica holding the key can open a handle; no ownership table is shared between replicas.

Three places to enforce it

agent→ gateway (P-AGW2995-SEAL)→ proxy (P2)→ MCP server (P1)

P1: inside the server, around the SDK's task manager. P2: a sealing proxy in front of an unchanged server. P-AGW2995-SEAL: agentgateway built from the open PR #2995 with an ExtMcp processor that seals and opens handles. P0 and P0-OFF (rmcp's own example) and P-AGW (agentgateway v1.6.0) are the baselines without an owner binding.

  1. Without an owner binding, the ID is enough. With rmcp's own Tasks example (P0-OFF) another caller reads and cancels the task; with an example-style server (P0) it also answers the task's question.
  2. A gateway that authorizes methods does not authorize tasks. agentgateway v1.6.0 refuses anonymous callers and agents outside its policy, but an allowed agent still reaches another agent's task.
  3. The sealed handle refuses every cross-tenant operation measured, in the server, in a proxy and in a gateway, and the refusal is indistinguishable from a task that does not exist.
  4. A proxy needs a NetworkPolicy. Without one, B calls the server directly and bypasses the proxy; with one, the bypass is blocked.
  5. The check can live in the gateway once the gateway runs a processor on tasks/* requests: PR #2995 adds that hook (not merged). Released agentgateway v1.6.0 does not run one there.
  6. Token lifetime is a separate matter. A revoked token keeps working where JWTs are validated locally, until shortly after it expires; introspection sees the revocation at once.

Kubernetes drain demo

Agent A starts draining a node that runs a payments workload protected by a PodDisruptionBudget, as a task. Agent B obtains the ID. Without a binding (P0, P-AGW), B forces the drain and the PodDisruptionBudget breaks. With P1, B is refused; with P2, B may watch a read-only handle but cannot force the drain.

Scope: this lab, with rmcp 3.5.1, agentgateway v1.6.0 and PR #2995 at 2bc5d041, Keycloak, and the configurations in the repository. The results say nothing about other SDKs or gateways.

Run it yourself

On Ubuntu 24.04 or 26.04 (4+ CPUs, 12 GB RAM, 40 GB disk). Tools that are already installed are left as they are; Docker and Python come from Ubuntu's own packages.

git clone https://github.com/graphsentinel/mcp-task-ownership.git && cd mcp-task-ownership
scripts/platform.sh install      # Docker, python3; kubectl, k3d, helm only if missing
scripts/platform.sh cluster-up   # k3d cluster: 1 server, 1 agent, 1 drain-demo node
scripts/lab.sh all               # build, helm install, run all tests, print the summary

On a fresh 8-CPU VM this took about 27 minutes and ended with ALL CHECKS PASSED. The lab can be removed and reinstalled without touching the cluster (scripts/lab.sh reinstall), and installed on an existing cluster with KUBE_CONTEXT and REGISTRY. Details are in the README.
